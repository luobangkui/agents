01 · 先统一概念

大家说的“动态挂载”，其实有两种

普通 Kubernetes CSI 挂载是 Pod 创建时确定 volume；本项目关心的是 Sandbox 已经预热运行后，用户创建沙盒时才决定挂哪块 VEPFS。

02 · 差异在哪里

为什么阿里 CSI 原路径可用，VEPFS 原路径不行？

关键不是云厂商名字，而是驱动要求的 CSI 生命周期不同。VEPFS 的 publish 依赖此前 stage 产生的节点级私有状态。

原有直挂型驱动路径

Direct Publish

agent-runtime 组装请求后，直接调用驱动的 NodePublishVolume，驱动能从请求和既有节点环境完成挂载。

简化链路
  1. 解析 PVC / PV
  2. 构造 NodePublishVolumeRequest
  3. 直接 NodePublish 到目标目录
阿里 NAS/OSS 在当前 agent_dp 既有路径中属于这类已验证的直接 provider。

VEPFS 驱动路径

Staged Lifecycle

VEPFS 的 NodePublishVolume 会读取 NodeStageVolume 生成的节点级 GPFS/VEPFS 状态，例如 driver-private info.json。

必须保持的顺序
  1. ControllerPublish / Attach
  2. NodeStage：加入或确认 mount service domain，生成 stage 状态
  3. NodePublish：基于 stage 状态发布给 Pod
只改请求参数、直接补一次 NodePublish 无法凭空制造 stage 状态，所以原 agent-runtime 直调会失败。

改造选择：不重写 VEPFS，也不和 kubelet 抢 CSI 状态

agent_dp 创建一个临时 Anchor Pod，把真实 PVC 交给 kubelet。这样 Attach、NodeStage、NodePublish 仍由 Kubernetes 和 VEPFS CSI driver 按标准顺序执行；agent_dp 只负责把 kubelet 已经挂好的结果传播进 Sandbox。

03 · 核心原理

Anchor Pod + mount propagation：把新挂载送进旧 Pod

点击四个状态查看链路变化。Sandbox 只接收传播，不需要 privileged；真正执行 bind/unmount 的是 agent_dp 管理的隔离 Anchor。

同一节点 · 同一 mount namespace 传播链
manager / agent_dp 解析 PVC、识别 VEPFS adapter、校验 mountServiceID 与节点 domain。
等待创建请求
kubelet + VEPFS CSI 为 Anchor Pod 执行标准 Attach → Stage → Publish，保留驱动私有状态。
尚未挂载
privileged Anchor Pod source 是 PVC；target 是 Sandbox emptyDir 的 hostPath，target 使用 Bidirectional。
Anchor 未创建
业务 Sandbox mount-root emptyDir 以 HostToContainer 注入；用户路径指向传播后的 bind mount。
/workspace/vepfs 不存在
请求前：预热 Sandbox 已经 Running，原 Pod spec 只有 mount-root 传播入口，没有 VEPFS PVC。
Bidirectional

Anchor → 节点

Anchor 内在 target 下创建的 bind mount 会反向传播到宿主机对应的 Sandbox emptyDir。

HostToContainer

节点 → Sandbox

宿主机 emptyDir 中出现的新 mount 再向下传播进已有业务容器。

普通业务权限

容器只消费结果

业务容器无需执行 mount，也无需 privileged；只通过固定目录和用户目标路径访问文件系统。

04 · 操作流程

从 API 请求到卸载清理，完整走一遍

切换标签查看预热命中、冷创建和删除卸载三条路径。挂载执行层复用同一个 staged CSI lifecycle adapter。

0

Pod 重建次数

命中带 mount-root 的同 domain 预热 Sandbox，锁定后动态创建 Anchor；原 Pod UID 保持不变。

  1. 用户 POST /sandboxes请求中传 templateID，以及 PVC 名称和目标路径 /workspace/vepfs。
  2. 解析 PV 生命周期adapter 识别 vepfs.csi.volcengine.com，解析 fsid、volumeHandle、mountServiceID 和只读属性。
  3. 筛选预热候选要求实际 Sandbox Pod 存在 mount-root；节点有 VEPFS CSINode；节点 domain 标签等于 PVC 的 mountServiceID。
  4. 锁定原 SandboxClaim 原有 Pod，不修改它的 volume spec，不重建 Pod。
  5. 在 PVC namespace 创建 AnchorAnchor 固定调度到 Sandbox 节点，source 挂 PVC，target 指向该 Pod UID 的 emptyDir hostPath。
  6. kubelet 完成标准 CSI 生命周期Attach / Stage / Publish 成功后，Anchor mounter bind 到 target/anchor/<stable-hash>。
  7. 传播并建立用户路径Bidirectional → HostToContainer 让旧容器看到 GPFS；runtime 把 /workspace/vepfs 指向稳定目标。
0

预热库存

没有可用 Sandbox 时，manager 在创建前把 mountService domain 约束注入 Pod 调度，不让 VEPFS 落错节点。

  1. 用户发出同样的 POST 请求业务层不需要区分 warm 或 cold，仍提供 templateID、PVC 和目标路径。
  2. 发现无兼容预热库存模板 replicas=0，或现有预热 Pod 不满足传播入口 / driver / domain 条件。
  3. 解析 PVC 的 mountServiceID本次实测解析为 mount-aed6284f。
  4. 注入 nodeSelector在真正创建 Sandbox 前写入 vepfs.csi.volcengine.com/mount-service=mount-aed6284f；冲突 selector 会被拒绝。
  5. Sandbox 调度到固定 domain 节点Pod 启动后已包含 mount-root，但仍不把业务 VEPFS PVC固化进原 Pod spec。
  6. 复用相同 Anchor 执行层后续 CSI、bind、传播和用户路径流程与 warm 完全一致。
204

DELETE 返回码

删除不是直接遗忘 Anchor。必须先正常 unmount 并确认挂载已消失，才清理路径和 Sandbox。

  1. 用户 DELETE /sandboxes/{id}manager 根据 Sandbox UID + 稳定 VolumeIdentity 找到它拥有的 Anchor。
  2. Anchor mounter 收到 SIGTERM执行正常 umount，不默认使用 lazy/force，避免脏数据和残留挂载。
  3. 校验 /proc/self/mountinfo只有目标确实不再挂载，mounter 才退出 0；busy 失败保留状态并等待重试。
  4. 清理 Sandbox 侧路径删除 agent_dp 创建的 symlink/目录，再移除 Anchor 和生命周期保护状态。
  5. 删除 Sandbox本次 warm/cold 两条实测均返回 HTTP 204，Sandbox CR、业务 Pod、Anchor 全部消失。
  6. 后台兜底30 秒 reconciler 回收 controller 崩溃、Sandbox 消失或 Pod UID 变化留下的 orphan Anchor。

06 · 谁负责什么

能力边界拆开后，问题就清楚了

VEPFS driver 没有被魔改；agent_dp 补的是 Sandbox 编排、生命周期适配和传播层。

组件/团队职责本次状态
agent_dp解析 staged CSI lifecycle；筛选/注入 domain；创建 Anchor；稳定身份；挂载回滚；同步卸载和 orphan reconciliation。已实现
Kubernetes / kubelet调度 Anchor；按照 PVC/PV 驱动执行 ControllerPublish、NodeStage、NodePublish；维护 Pod volume 生命周期。复用标准能力
VEPFS CSI driver完成 VEPFS/GPFS 的标准 attach、stage、publish、unpublish；维护 driver-private stage 状态。无需改造
节点运维一个节点固定一个 mountServiceID；确认真实 client/domain 后打标签；节点重启/重装后重新核验。需固化 SOP
业务调用方创建 Sandbox 时提交 templateID、PVC 名称和目标路径；DELETE Sandbox 触发卸载。接口保持简单
07 · mountService domain

固定 domain 模型下，这个限制不是卡点

节点标签不是用来“假装加入”某个 domain，而是把节点真实状态告诉调度和 manager，阻止 PVC 落到错误 mount service。

节点真实状态VEPFS client 已加入 mount-aed6284f，boot/client 状态有效。
＋
运维标签mount-service=mount-aed6284f
＝
安全调度域只接收相同 mountServiceID 的 VEPFS PVC。

你们当前模式

mountServiceID 一对一固定到节点池，正常运行期间不切换。这正好匹配当前实现，已经具备上线条件。

唯一需要守住

节点重启、重装、client 异常后，要重新确认真实 domain 再保留/恢复标签，避免出现“标签还在，实际 VEPFS 状态已失效”。

08 · 边界与结论

什么已经 Ready，什么还没有

把边界讲清楚，才能让“支持动态挂载”成为可以验收的结论，而不是一句模糊口号。

READY

当前可以承诺

  • 创建 Sandbox 时指定 VEPFS PVC 和目标路径
  • 命中已运行的同 domain 预热 Sandbox
  • 无库存时自动注入 domain 的冷创建
  • 不重建预热 Pod、不重启业务容器
  • DELETE 时正常 unmount、清理 Anchor 与路径
  • 节点长期固定 mountServiceID 的生产模型
FOLLOW-UP

需要继续补齐

  • Sandbox pause/hibernate → resume 后自动恢复 staged mount
  • VCI 节点（没有普通节点的 hostPath/CSINode 条件）
  • 节点在线跨 mountServiceID 切换与 vendor leave/reset
  • manager 在 Binding/Unbinding 中途重启等扩展故障注入矩阵
  • 火山 EFS+FSx、腾讯等驱动的独立 lifecycle adapter
FINAL VERDICT

固定 mountServiceID 的创建/预热池场景，VEPFS 动态挂载已经 Ready

VEPFS driver 继续负责它擅长的 staged CSI 生命周期；agent_dp 通过 Anchor、domain-aware placement 和 mount propagation 补齐“已有 Sandbox 如何看到新挂载”这一层。核心 warm、cold、I/O、unmount 链路已经在真实火山集群闭环。
